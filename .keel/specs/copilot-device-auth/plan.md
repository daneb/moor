# Design — copilot-device-auth

## Approach

The seam is **secret resolution** — `secrets::resolve_into_env`, which
already fills the sandbox's env from the shell then moor's own Keychain
entries. This change adds one more, lowest-priority source for exactly one
secret: the Copilot CLI's own device-flow token.

1. **A `copilot_device_token() -> Option<String>` in `secrets.rs`** that
   reads the macOS Keychain service `copilot-cli` (where `copilot /login`
   stores a `gho_` OAuth token — verified locally). Pure wrapper over
   `security find-generic-password -s copilot-cli -w`; returns `None` on
   any miss/error, never panics (AC-1, AC-6). It does not require a moor
   `secrets set` (AC-1), is read fresh on each call (AC-4), and its value
   never enters an argv — the `-w` read is captured from stdout, and
   injection uses the existing env mechanism (AC-5).

2. **In the resolution path (`up.rs` via `resolve_into_env`)**, after the
   existing env+Keychain resolution, if the project's agent is `copilot`
   (manifest `agent` field from SPEC-0010) AND `COPILOT_GITHUB_TOKEN` is
   still unresolved, fall back to `copilot_device_token()`. The explicit
   sources win (AC-2); non-copilot projects never trigger it (AC-3).

3. **Redaction is automatic**: resolved secret values already flow through
   `audit::redact`, which scrubs any resolved secret value from logged
   execs — the device token, once resolved into the env map moor redacts
   against, is covered the same way (AC-7). The change adds the value to
   that same redaction set, not a new path.

Nothing is persisted: the token is read at resolution time and injected
into the container's env, never written to the manifest, compose file, or
a moor Keychain entry (AC-4) — so an expired/rotated device token is
simply re-read next `up`.

## Scope note

`compose.rs` is in scope because the injected env var must appear in the
rendered compose env list for the sandbox to receive it; the resolution
logic itself lives in `secrets.rs`/`up.rs`.
