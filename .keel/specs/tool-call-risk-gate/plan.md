# Design — tool-call-risk-gate

## Approach

The seam is `run_cmd::run`, the one place a `moor run <project> -- <cmd>`
argv turns into `docker exec`. Everything else is additive around it:

1. `cli/src/decision.rs` — a new, dependency-free module. `pub enum
   Verdict { Allow, Deny { rule_id: &'static str, reason: String } }` and
   `pub fn evaluate(cmd: &[String]) -> Verdict`, backed by three private
   rule functions (`credential_access`, `boundary_escape`,
   `destructive_wipe`), one per AC-2/3/4. Pure function, no I/O, so it is
   tested directly with no fixture.
2. `cli/src/audit.rs` — one new function, `log_decision(path: &Path,
   project: &str, cmd: &[String], secret_names: &[String], rule_id: &str)
   -> Result<()>`. It calls the existing `redact_argv` + `append_chained`
   directly, like `verify_chain` does, rather than going through
   `log_exec_with` — a command that never ran has no keel sink to fold and
   no project dirs to lazily create, so it takes an already-resolved
   `&Path` instead of a project name. This is also what keeps AC-5's
   oracle a real unit test: no dependency on `$HOME`/`paths::*`/Docker.
3. `cli/src/commands/run_cmd.rs` — a small private `fn gate(chain_path:
   &Path, name: &str, secrets: &[String], cmd: &[String]) -> Result<()>`
   that calls `decision::evaluate`, and on `Deny` calls
   `audit::log_decision` then returns the rule's `Err` before anything
   Docker-related is constructed. `run()` calls `gate(...)?` once, right
   after resolving the manifest and secrets, before it builds `docker
   exec` args. An `Allow` verdict makes `gate` a no-op `Ok(())`; the rest
   of `run()` is untouched.
4. `cli/src/main.rs` — add `mod decision;` next to the other top-level
   modules.
5. `docs/adr/0001-tool-call-risk-gating.md` — records the finding that
   led here (an in-sandbox agent hook is not the enforcement point,
   `docker exec` in `moor run` is), the question schema this rule table
   is a fixed-rules stand-in for, and what is explicitly deferred (model,
   daemon, "ask").

`docs/THREAT-MODEL.md` stays in scope but untouched unless G1/G2 turns up
a reason to add a breakout-list entry for this control; the smallest
change that satisfies the criteria doesn't require it.
