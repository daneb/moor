# Design — spec-abandonment

## Approach

moor drives keel over the sandbox boundary; this change adds one guided verb
and makes the guidance layer aware of keel's new `abandoned` terminal state
(the keel half is the companion spec in ../keel).

1. **`moor drop "<why>"` (cli/src/commands/flow_cmd.rs).** A sibling of
   `reject`, built on the same `Target::resolve` + `exec` seam. It refuses an
   empty/whitespace reason (AC-2), then runs keel's own abandon command in the
   sandbox — `keel spec abandon <active-slug> --reason <why>` — resolving the
   active spec from `moor next` exactly as `reject` does, so the operator never
   types a slug or stage (AC-1, AC-6). It ends by printing `moor next`'s
   guidance for where that left things, like the other flow verbs.

2. **Distinct boundary (cli/src/commands/flow_cmd.rs).** `drop` sends keel the
   `spec abandon` command; `reject` keeps sending `approve --reject`. Nothing
   routes a drop through the rejection path or vice-versa, so the two decisions
   can never be confused at the boundary (AC-3). This mirrors the studio Host's
   separate `approve`/`reject` methods.

3. **Guidance awareness (cli/src/guide.rs).** `NextSpec.complete` already comes
   straight from keel's `complete` flag, which the keel half sets true for an
   abandoned spec (companion AC-2). So `pick_active`'s existing `!complete`
   filter drops an abandoned spec with no change (AC-4) — the test pins that it
   stays dropped. `step_label` gains an `abandoned` arm returning the label
   `abandoned` rather than a step number (AC-5).

4. **Wiring (cli/src/main.rs, cli/src/commands/mod.rs).** Add the `Drop`
   subcommand and dispatch it to `flow_cmd::drop`, beside `Reject`.

AC-7 and AC-8 assert the keel-side contract this relies on and are verified by
a human against a keel build carrying the companion change; no moor code proves
them. They stay in this spec so moor's dependency on that contract is explicit
and traced.

## Rollback

`git revert` of the implementing commits. The change is additive — a new
`moor drop` verb and two guidance arms — so reverting restores the prior
command set and `guide` behaviour with no migration. Any spec keel has marked
`abandoned` simply becomes visible again as open if moor is reverted while keel
is not; that is harmless and matches pre-change behaviour.
