# Design — drop-serde-yaml

## Approach

**The seam: the `serde_yaml::` import path itself.** `yaml_serde` is a
maintained fork whose public surface (`from_str`, `to_string`, `Value`,
the `Serialize`/`Deserialize` derives) matches the code's existing usage,
so the migration is a dependency swap plus a mechanical path rename, not
a behavioural rewrite.

Steps, smallest surface first:

1. In `cli/Cargo.toml`, replace `serde_yaml = "0.9"` with
   `yaml_serde = "0.10"`; update `cli/Cargo.lock` via `cargo build`.
   `unsafe-libyaml` leaves the tree with `serde_yaml`.
2. Rename every `serde_yaml::` path to `yaml_serde::` across the 5
   source files (14 call sites) — `from_str`, `to_string`, and
   `Value` reads, in both production code and tests. No signatures, error
   messages, or control flow change.
3. Prove parity, not just compilation: the existing `manifest::tests`
   round-trip (save → load → equal) and the `spec_cmd`/`recipe`
   front-matter tests are the oracle that behaviour is unchanged; they
   pass against the new crate without being modified.
4. `cargo deny check advisories` goes green because the advisory's source
   crate is gone — that is the whole point, asserted directly (AC-4).

The +1 dependents (`mod.rs`, `main.rs`, `ask_cmd.rs`, `up.rs`) import the
changed modules but contain no `serde_yaml` usage of their own (verified);
they only need to keep compiling, which the signature-preserving swap
guarantees.
