# Design — tool-call-ask-verdict

## Approach

The seam is still `run_cmd::gate`, the function ADR-0001/SPEC-0008 added.
It changes what happens on a `Deny` from `decision::evaluate`, not
whether one fires:

1. `cli/src/commands/run_cmd.rs` — three new small functions: `confirm`
   (prints the rule id/reason, reads one line, true only for `y`/`yes`),
   `stdin_is_tty` (`std::io::IsTerminal`), and `operator_identity` (`git
   config user.name`, falling back to `unknown`). `gate` grows an
   `interactive: bool` plus a `reader`/`writer`/`operator` it is handed
   rather than reads itself — the same dependency-injection shape
   `chain_path` already used, so the confirm/decline/non-interactive
   paths are unit-tested with a `Cursor` instead of a real terminal.
   `allowed = interactive && confirm(...)` — the `&&` short-circuit is
   what makes a non-interactive invocation never touch stdin at all,
   satisfying AC-3 by construction, not by a separate check.
2. `cli/src/audit.rs` — `log_decision` gains `allowed: bool` and
   `operator: &str`, and the entry's `verdict` field changes from
   `"deny"` to `"ask"` with a new `resolution` field (`"allow"`/`"deny"`)
   and `"by"`. Same function, same call site, more fields — no new
   function.
3. `docs/adr/0002-tool-call-ask-verdict.md` — records the decision and,
   explicitly, the `moor recipe` gap found while scoping this (Docker
   called directly, bypassing `gate` entirely) as still open.

`run()`'s call site changes only in what it passes to `gate`: real stdin,
real stderr, the real TTY check, the real operator identity. Everything
after the `gate(...)?` call — building the `docker exec` argv, the
push/exec audit entry — is untouched.
