# Turn a studio conversation into a spec

## Context

The way a feature starts today is split across places: you brainstorm with
the agent (`moor ask`, or studio's input), then write a spec file on the
host by hand, then `moor spec push` it — or you write a recipe file and
run `moor recipe`. The thinking and the artefact live in different tools,
so the step from "we worked out what to build" to "there is a spec" is
manual retyping.

Studio already holds the conversation and already edits artefacts in the
sandbox (`edit_artifact`, write-back through `docker exec -i`, no bind
mount). And moor already has the piece that makes this safe:
`session::emit_recipe` writes an agent answer to a draft, **parses it
first**, and only moves it into place if it is a well-formed recipe —
otherwise it keeps the draft and says so. `moor ask --emit-recipe` uses
exactly that.

So the missing step is small: a key in studio that takes the answer
currently on screen and turns it into a spec for that project, reusing the
parse-before-write guard rather than trusting the agent's output.

## Acceptance criteria

### AC-1 A key turns the current answer into a spec draft

WHEN the operator presses the author key while an agent answer is on
screen THE SYSTEM SHALL write that answer as a spec draft for the selected
project.

oracle: cmd `cargo test --manifest-path cli/Cargo.toml author_key_drafts_a_spec_from_the_answer` exit 0

### AC-2 Nothing is written when there is no answer

IF the operator presses the author key and the selected project has no
agent answer yet THEN THE SYSTEM SHALL write nothing and say why.

oracle: cmd `cargo test --manifest-path cli/Cargo.toml author_without_an_answer_writes_nothing` exit 0

### AC-3 A draft that does not parse is kept as a draft, not installed

IF the answer does not parse as the expected artefact THEN THE SYSTEM
SHALL leave it as a draft file and report that, rather than installing it
as the project's spec.

oracle: cmd `cargo test --manifest-path cli/Cargo.toml unparseable_answer_stays_a_draft` exit 0

### AC-4 A drafted spec is reported with the command that checks it

WHEN a spec draft is written THE SYSTEM SHALL show the next command that
checks it, so the operator is not left guessing the pipeline step.

oracle: cmd `cargo test --manifest-path cli/Cargo.toml drafted_spec_names_the_next_command` exit 0

### AC-5 The answer is sanitized before it becomes an artefact

WHEN an agent answer is written to a draft THE SYSTEM SHALL strip
terminal control sequences from it first, as studio already does before
drawing it.

oracle: cmd `cargo test --manifest-path cli/Cargo.toml authored_draft_is_sanitized` exit 0

### AC-6 Authoring is recorded like any other sandbox action

WHEN a spec is authored from studio THE SYSTEM SHALL record the action in
the project's audit trail, as studio's other sandbox actions are.

oracle: cmd `cargo test --manifest-path cli/Cargo.toml authoring_is_recorded` exit 0

### AC-7 The host writes the draft; the sandbox is not asked to author it

WHEN a draft is written THE SYSTEM SHALL write it from the host (or
through the same `docker exec` stdin path `edit_artifact` uses) rather
than asking the agent inside the sandbox to write its own spec file.

oracle: cmd `cargo test --manifest-path cli/Cargo.toml draft_is_written_by_the_host` exit 0

### AC-8 Existing CLI tests stay green

THE SYSTEM SHALL leave the existing CLI test suite passing.

oracle: cmd `cargo test --manifest-path cli/Cargo.toml` exit 0

## Out of scope

- Rejection and gate output in studio — sibling spec `studio-decisions`.
- Authoring a *plan* from a conversation: the plan is generated by `keel
  plan` from an approved spec, and its approach section is a human edit
  (`e` already opens it). This spec covers the spec artefact only.
- Approving the authored spec: that is a decision, and it stays an
  explicit human act at the existing approval gate.
- Replacing `moor spec push` or `moor recipe`; both keep working. This adds
  a path from a conversation already in studio.
