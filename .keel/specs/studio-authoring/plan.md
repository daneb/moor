# Design — studio-authoring

## Approach

The seam is **`session::emit_recipe`**, which already does the hard part:
it writes an agent answer to a draft, parses it, and only installs it if
it is well-formed — keeping the draft and saying so otherwise. Studio
gains a key that feeds it the answer on screen. Nothing new is invented;
the conversation is routed into the guard that already exists.

1. **`state.rs`: a new key and action.** `s` (free — `q`/`r`/`a`/`e`/`x`
   are taken) emits `Action::AuthorSpec { project, body }`, where `body`
   is the text of the **last `Line::Agent`** in that project's transcript.
   - AC-2: with no `Line::Agent` yet, no action is emitted and the status
     line says there is no answer to author from.
   - AC-5: the body passes through the existing `render::sanitize` before
     it leaves `state.rs`, so nothing that reached the transcript from a
     sandbox can carry control sequences into a file.
   - `s` is a command only on an empty input line, like the other keys, so
     typing the letter mid-question still types it.

2. **`mod.rs`: the action writes the draft, host-side.** The handler calls
   `session::emit_recipe(dest, body)` where `dest` is a path on the host
   (`<project>-<timestamp>.recipe.md` in the working directory). AC-7 is
   satisfied by construction: this is a host-side `std::fs` write through
   `emit_recipe`, and the sandbox is never asked to author its own spec
   — no `docker exec`, no agent turn.
   - AC-3: `emit_recipe` already returns the "kept as a draft" outcome
     when the body does not parse as a recipe; the handler surfaces that
     as a console note rather than installing anything.
   - AC-4: on success the note names the command that takes it on —
     `moor recipe <project> <file>` — so the operator is not left to
     work out the pipeline step.
   - AC-6: the handler appends one entry to the project's chain with
     `audit::append_chained(chain_log_path(project), "studio-author", …)`,
     carrying the project, the destination and a SHA-256 of the body —
     the hash rather than the text, matching how `session`'s `agent-turn`
     entry keeps content out of the chain.

3. **A recipe, not a spec.md, is the artefact.** A new spec has no slug
   yet, so there is no `.keel/specs/<slug>/` to write into; a recipe is
   moor's existing input for "a loose description that becomes a spec",
   and `moor recipe` already drives it through G0 and the approvals. This
   keeps the change to one new key and one new handler, and leaves
   `moor spec push` and `moor recipe` working exactly as they do.

`Action` is a plain enum and the key handling is a pure function of
`Console`, so AC-1/AC-2/AC-5 are asserted on what `handle_key` returns
with no terminal. AC-3/AC-4/AC-6/AC-7 are asserted against a temporary
directory and the chain file, with no container.
